# PilotCraft independent audit — October 22, 2026

Scope: backend, model orchestration, runtime validation, browser request handling, report rendering/export, evaluation harness, CI, and installed dependency advisories. This is an audit; application code and dependencies were not changed.

## Verification

- All 74 existing tests passed. Initial failures were caused by restricted localhost connections; rerunning with local connections allowed passed.
- Type checking and the production build passed. The initial build was blocked by filesystem restrictions; the unrestricted build succeeded.
- Additional temporary probes used fake model responses and made no Gemini API calls. They confirmed findings 1–3 and 5 below. The temporary probe was removed.
- The current npm advisory scan reported three affected packages: one critical and two high. These are package advisory classifications, not proof that every vulnerability is exploitable through PilotCraft.
- No live Gemini quality evaluation or interactive browser/accessibility audit was performed. Findings 6–7 come from source review.
- The pre-existing modification to `evals/fixture-results.md` was preserved.

## Findings, ordered by priority

### 1. [P1] Forwarded headers can bypass the rate limiter on direct connections

Location: `app.ts:198`, `app.ts:239`.

The app unconditionally sets `trust proxy` to one hop, including local/direct deployments. A directly connected caller can choose the address Express uses for `req.ip` by supplying `X-Forwarded-For`, which is also the rate-limit key.

Reproduction: nine valid requests over the same localhost connection source, each with a different forwarded address, all returned HTTP 200 and reached the model stub. The documented limit is eight. This allows a directly reachable instance to incur model costs without the intended per-IP restriction.

Deployment qualification: an enforced reverse proxy that correctly rewrites/appends the header and prevents direct origin access can avoid this particular bypass. That deployment guarantee is not established by this repository's unconditional setting.

Recommendation: default to trusting no proxy; explicitly configure trusted proxy addresses for the deployment, enforce the origin boundary, and test both direct and proxied requests. Add a separate global/concurrency budget for paid calls if exposing the app publicly.

### 2. [P2] Repair requests lose the original scenario

Location: `runAnalysisRoute.ts:77`–`87`.

The initial model call receives the scenario. A repair is a separate generation request containing only validation errors and the previous response. It includes neither the original scenario nor conversation history. If the first output is truncated or omits an important condition, the repair has no authoritative source from which to restore it. A schema-valid response can then be displayed as a successful assessment of the user's request.

Reproduction: the first stub response was `{}`; the second call's contents did not include a unique marker from the original scenario. Returning any structurally valid report from the repair produced a result event.

Recommendation: include the original scenario in every repair, clearly separated from the invalid output, and require preservation of scenario facts. Add a regression assertion on the actual repair request contents.

### 3. [P2] Empty reports pass validation and can imply that evidence is complete

Locations: `validation.ts:9`, `validation.ts:46`, `validation.ts:54`, `validation.ts:62`; `src/components/ReportDisplay.tsx:119`.

All arrays allow zero items, and common string arrays allow empty strings. A report can therefore contain no workflow, risks, pilot phases, success metrics, evidence, or decision criteria and still pass. The browser labels an empty missing-evidence list “Information complete,” and the Markdown export makes the same assertion.

Reproduction: replacing every array in the valid test fixture, including nested arrays, with `[]` still passed `analysisReportSchema.safeParse`.

Recommendation: require useful content in core planning sections, trim and reject blank entries, and use explicit handling for a deliberately inapplicable section. Replace “Information complete” with neutral wording unless completeness has actually been established. Test these boundaries through the repair/fallback pipeline.

### 4. [P2] Installed dependencies have current security advisories

Locations: `package-lock.json:3270`, `package-lock.json:3591`, `package-lock.json:4235`.

The installed versions and current scan results are:

| Package | Installed | Scan severity | Exposure qualification / patch |
| --- | --- | --- | --- |
| proxy-addr | 2.0.7 | Critical | The advisory concerns particular IPv4-mapped IPv6 trust-subnet configurations. PilotCraft uses numeric hop trust, so that specific prerequisite was not found here. Patched in 2.0.8. |
| source-map-js | 1.2.1 | High | Malicious indexed source maps can block the event loop. No public route accepting attacker-supplied source maps was identified. Patched in 1.2.2. |
| vite | 6.4.3 | High | The scan lists several advisories, including Windows editor command handling. Relevant to the development server; a correctly configured production run does not mount Vite middleware. The reviewed Windows advisory lists 6.4.4 as patched. |

Sources: [proxy-addr advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h), [source-map-js advisory](https://github.com/advisories/GHSA-68fv-2mgg-jv7q), [Vite/launch-editor Windows advisory](https://github.com/advisories/GHSA-587h-7wmj-h5pm).

Recommendation: update to patched compatible versions, regenerate the lockfile, and rerun tests/build/audit. Add dependency scanning to CI. Do not describe the package-level critical alert as a demonstrated critical exploit in this app; finding 1 is the separately demonstrated rate-limit issue.

### 5. [P2] Empty model output skips the backup model

Locations: `runAnalysisRoute.ts:116`, `analysisRepair.ts:43`, `retry.ts:6`.

An empty initial response throws “Empty response from Gemini.” An empty repair throws a similar error. Neither matches the retry classifier. These unusable outputs therefore end the assessment even when the backup model could succeed, whereas nonempty malformed/schema-invalid responses receive repair/fallback handling.

Reproduction: an empty primary stub response and a working backup stub produced calls to only the primary, followed by status/error events and no result.

Recommendation: classify unusable model output explicitly and route empty initial/repair responses through the bounded repair/fallback policy. Preserve distinct handling of upstream safety blocks when finish-reason metadata is available.

### 6. [P2] A stream that ends without a result silently stops loading

Location: `src/App.tsx:77`–`109`.

The browser exits its read loop when the stream ends without checking whether it received a result or an explicit error. If an intermediary closes the stream cleanly after a status event, the interface simply stops loading. On a first request it returns to the empty state; if a prior report exists, that old report remains with no indication that the new assessment never completed.

Recommendation: track completion, show an interrupted-assessment error on EOF without a result, and associate displayed reports with the scenario that generated them. Cover a status-only stream and interruption during regeneration.

### 7. [P2] The core input and loading state lack accessible names/announcements

Locations: `src/App.tsx:152`–`178`, `src/App.tsx:241`–`265`.

The scenario textarea has an ID and placeholder but no associated label or accessible name. During loading, the Generate button contains only a decorative spinner with no text label. Status and error messages also lack live-region/alert semantics, so users of assistive technology may not hear progress or failures.

Recommendation: add an associated label, retain a text or accessible label on the loading button, and expose status/error changes using appropriate live-region semantics. Verify with keyboard and screen-reader use; these source findings do not constitute a full accessibility assessment.

## Smaller follow-ups

- The input has no `maxLength` or character counter despite the server's 4,000-character cap (`src/App.tsx:152`). Users discover oversized input only after submission.
- Markdown table values are interpolated without escaping pipes/newlines (`src/reportToMarkdown.ts:53`, `84`, `126`), so model text can break exported table structure.
- The UI shows only the first three readiness-reducing factors (`src/components/ReportDisplay.tsx:71`), while Markdown retains all of them. Additional factors have no expansion control.
- Live evaluation artifacts retain check summaries but omit the original generated reports and actual successful model IDs (`evals/runEval.ts:68`, `139`). This limits independent inspection of the reported quality results.

Suggested order: close the direct-access rate-limit bypass; preserve repair context; strengthen meaningful report validation; patch dependencies; then address stream/fallback behavior and accessibility.
